# 2026-05-31 작업 기록

## 1. 작업 요약

오늘은 전투 시스템 구조 정리, 소환 후보 뽑기 흐름 정리, Plate 표시/상태 안정화, QA 우선순위 정리, 씬 구조 정리, Agent 역할 분리 규칙 정리를 진행했다.

- 전투 소환수의 상태이상 처리와 공격 처리 책임을 분리했다.
- 승리/패배 결과 처리에서 Alert 표시, 진행 저장, 스테이지 정보 책임을 나눴다.
- 소환수 이미지, 상태 색상, 효과음 표시를 View 컴포넌트로 분리했다.
- `Plate` 전투 칸의 상태 동기화, 대상 조회, 표시/하이라이트 책임을 정리했다.
- `Draw` 소환 후보 뽑기와 `Redraw` 다시 뽑기 이름을 정리하고 관련 버튼 이벤트 이름을 맞췄다.
- QA 인덱스를 다시 확인하고 PlayMode 차단 항목과 Fail 항목을 분리했다.
- HUD와 Fight 1Stage 씬 Hierarchy를 역할별 그룹으로 정리했다.
- DevAgent와 QAAgent가 한 세션 안에서 절대 전환되지 않도록 운영 규칙을 명시했다.

역할:
- 이 날짜 파일은 날짜별 공용 기록이다.
- 각 작업 항목은 DevAgent 또는 QAAgent 역할을 별도로 표시한다.
- 한 작업 항목 안에서 역할은 전환하지 않는다.

---

## 2. 작업 배경

이 작업을 진행한 이유는 다음과 같다.

- 기존 문제:
  - 전투 소환수 코드가 상태이상 계산, 공격 처리, 이미지/색상/효과음 표시를 함께 담당해 구조를 이해하기 어려웠다.
  - 전투 승리/패배 처리에서 UI Alert, 스테이지 진행 저장, 현재 스테이지 정보가 섞여 있었다.
  - `Plate`는 전투에서 소환수가 배치되는 칸인데, 칸 상태 관리와 화면 표시가 `PlateController`에 함께 들어 있었다.
  - `Draw`는 소환 후보를 뽑는 흐름인데, Take/ReTake 같은 이름과 Draw/Redraw 이름이 섞여 있었다.
  - PlayMode 테스트가 timeout 또는 connection error로 막히는 항목이 많아, 실제 코드 Fail과 실행 환경 Blocked를 구분해야 했다.
  - HUD와 Fight 1Stage 씬의 오브젝트가 역할별로 정리되어 있지 않아 새 작업자가 구조를 파악하기 어려웠다.
- 작업 목적:
  - 전투 규칙, 화면 표시, 저장 진행, QA 기록 책임을 분리한다.
  - 소환 후보 뽑기와 다시 뽑기 흐름의 이름을 이해하기 쉽게 맞춘다.
  - QA 항목의 상태를 Pass, Fail, Blocked, Fixed, Closed로 명확히 관리한다.
  - WorkLog만 봐도 새 작업자가 그날 무엇을 했고 무엇이 남았는지 이해할 수 있게 한다.
- 관련 기능:
  - BattleCore: 턴, 공격, 상태이상, 승리/패배 판정
  - BattleContent: 소환 후보 뽑기, Redraw, Plate 배치
  - SceneObject: HUD, Fight 1Stage Hierarchy
  - QAReports: 전체 QA 우선순위와 버그 상태
  - Agents: DevAgent/QAAgent 역할 운영 규칙

### 3.1 DevAgent - 전투 상태이상과 공격 처리 구조 분리

#### 변경 전

기존에는 다음과 같은 문제가 있었다.

- `Summon`이 상태이상 적용, 공격 가능 여부, 공격 후 연출까지 많이 담당했다.
- 공격 타입별 효과 적용 흐름이 여러 전략 클래스에 직접 들어 있어 변경 범위가 컸다.

#### 변경 후

다음과 같이 수정했다.

- 독, 화상, 회복, 보호막 같은 상태이상 처리를 `StatusEffectController`와 상태별 객체로 분리했다.
- 단일 공격, 전체 공격, 가까운 적 공격의 효과 적용을 공격 타입별 객체로 분리했다.
- 고양이 특수공격의 기존 전투 공식과 대상 선택 방식은 유지했다.

#### 관련 파일

- `Assets/Script/Summons/Summon.cs`
- `Assets/Script/Battle/Status`
- `Assets/Script/Battle/Attack`

### 3.2 DevAgent - Battle 승리/패배 처리 흐름 분리

#### 변경 전

기존에는 다음과 같은 문제가 있었다.

- 전투 결과 처리에서 Alert View와 스테이지 진행 저장 로직이 직접 얽혀 있었다.
- 전투씬 단독 실행 시 씬에 없는 StageController를 찾을 수 있어 NullReference 위험이 있었다.

#### 변경 후

다음과 같이 수정했다.

- 전투 결과 판단은 `BattleResultController`가 담당하게 했다.
- 스테이지 진행 저장은 `BattleProgressController`가 담당하게 했다.
- 현재 전투 스테이지 정보는 `BattleStageContext`가 담당하게 했다.
- `Player`는 Alert View를 직접 호출하지 않고 결과 컨트롤러를 거치게 했다.

#### 관련 파일

### 3.5 DevAgent - Draw 진행 상태와 이름 정리

#### 변경 전

기존에는 다음과 같은 문제가 있었다.

- 일반 Draw가 시작돼도 “소환 진행 중” 상태가 켜지지 않아 후보 선택 중 다른 입력이 들어올 수 있었다.
- 소환 후보 뽑기 흐름에서 Take/ReTake, Draw/Redraw 이름이 섞여 있었다.
- 재소환 버튼 이벤트 이름이 오래된 의미를 담고 있었다.

#### 변경 후

- 일반 Draw 시작 시에도 `SummonController`가 소환 진행 중 상태로 들어가도록 했다.
- `SummonController` 내부 이름을 Draw/Redraw 기준으로 맞췄다.
- 재소환 버튼 handler 이름을 `OnRedrawButtonClick`으로 바꾸고 Fight Scene UnityEvent 연결도 갱신했다.
- 기존 씬 참조가 깨지지 않도록 직렬화 필드는 안전한 이름 변경 방식을 사용했다.

### 3.6 DevAgent - Draw Option Panel View 이름 정리

#### 변경 전

기존에는 다음과 같은 문제가 있었다.

- 소환 후보를 보여주는 패널 이름이 `PickSummonPanelView`로 남아 있어 Draw/Redraw 용어와 맞지 않았다.
- 새 작업자가 소환 후보 뽑기 UI 역할을 이름만 보고 이해하기 어려웠다.

#### 변경 후

다음과 같이 수정했다.

- `PickSummonPanelView`를 `DrawOptionPanelView`로 이름 변경했다.
- `SummonController`의 draw/redraw option panel 필드 타입을 새 이름에 맞췄다.
- Unity script GUID가 유지되도록 `.meta` 파일을 함께 이동했다.
- 새 class/file 이름과 GUID 유지 여부를 확인하는 정적 테스트를 추가했다.
- `DrawOptionPanelView`가 `SummonController.Instance`를 직접 호출하지 않도록 선택 handler를 받는 구조로 바꿨다.
- `SummonController`가 Draw/Redraw option panel 선택 이벤트를 `OnSelectSummon`에 연결한다.
- `SummonController.Instance` static field와 assignment를 제거했다.

#### 관련 파일

- `Assets/Script/Battle/SummonPick/DrawOptionPanelView.cs`
- `Assets/Script/Battle/SummonPick/SummonController.cs`

### 3.8 DevAgent - 공격 대상 조회와 공격 예외 방어

#### 변경 전

기존에는 다음과 같은 문제가 있었다.

- PlateController의 player/enemy 대상 조회 이름과 실제 기준이 헷갈릴 수 있었다.
- 단일 대상 공격에서 대상 목록이 없거나 index가 잘못되면 예외가 날 수 있었다.

- 여러 공격 전략에 null Plate, 빈 대상, 잘못된 특수공격 배열 접근을 막는 guard를 추가했다.

### 3.12 DevAgent - DevAgent와 QAAgent 역할 분리 및 warning 확인 규칙 추가

#### 변경 전

기존에는 다음과 같은 문제가 있었다.

- 같은 날짜 WorkLog에 개발 기록과 QA 기록이 함께 있어 역할이 전환된 것처럼 보일 수 있었다.
- 테스트가 Passed로 끝나도 warning, missing script, 자동 복구 로그가 있으면 실제 프로젝트 상태가 안전하지 않을 수 있었다.

#### 변경 후

다음과 같이 정리했다.

- DevAgent는 개발, 수정, 테스트 추가, QA 요청 작성까지만 담당한다고 명시했다.
- QAAgent는 MCP 기반 검증, 결과 기록, Dev Fix Request 작성만 담당한다고 명시했다.
- Pass/Closed 판정 시 실패 개수뿐 아니라 warning, error, exception, missing script/component, 자동 복구 로그도 확인하도록 했다.
- WorkLog 작성 기준을 프로젝트를 처음 보는 사람도 이해할 수 있는 형식으로 바꿨다.

#### 관련 파일

- `Assets/RefactRoadMap/Agents/DevQAWorkflow.md`
- `Assets/RefactRoadMap/Agents/DevAgent.md`
- `Assets/RefactRoadMap/Agents/QAAgent.md`

## 5. 발생한 문제와 해결

### 문제

PlayMode 테스트가 timeout 또는 connection error로 끝났고, 일부 전투 진입 재시도 중 `Summon.Update()` line 77 NullReferenceException이 확인됐다.

### 원인

PlayMode 실행 자체는 MCP/Unity 연결 문제로 차단됐다. 별도로 확인된 `Summon.Update()` NullReferenceException은 소환수 View 초기화가 모든 파생 소환수에서 보장되지 않는 구조가 원인으로 의심된다.

### 해결

QAAgent는 코드 수정하지 않고 `BUG-BC-002`로 Fail 기록과 Dev Fix Request를 남겼다. `BUG-BC-001` 승리 Alert는 정적 연결만 통과했으므로 `Fixed/Blocked`로 유지했다.

### 문제

일부 MCP 요청은 첫 실행에서 timeout 됐다.

### 원인

Unity Editor 또는 MCP 연결 상태가 일시적으로 불안정했다.

### 해결

가능한 경우 같은 검증을 재시도해 재컴파일 warning 0과 EditMode 테스트 통과를 확인했다. 재시도해도 PlayMode가 막힌 항목은 Blocked로 남겼다.

## 7. 참고 메모

추후 다시 볼 수 있는 메모다.

- BattleCore는 턴, 공격, 상태이상, 승리/패배 판정을 담당한다.
- BattleContent는 소환 후보 뽑기, 소환수 배치, 적 AI 같은 콘텐츠 흐름을 담당한다.
- `Plate`는 전투에서 소환수가 배치되는 칸이다.
- `Draw`는 소환 후보를 뽑는 흐름이고, `Redraw`는 후보를 다시 뽑는 흐름이다.
- QA에서 PlayMode timeout은 코드 Fail과 섞지 않고 Blocked로 기록한다.
- `Closed`는 QAAgent가 Fixed 항목을 재검증해 통과했을 때만 기록한다.
- UnityEvent가 참조하는 public 메서드 이름은 씬 연결을 깨뜨릴 수 있으므로 변경 전 연결 상태를 먼저 확인한다.
