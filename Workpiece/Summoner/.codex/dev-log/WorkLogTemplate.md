# YYYY-MM-DD 작업 기록

## 작성 기준

이 문서는 프로젝트를 처음 보는 사람도 작업 맥락을 이해할 수 있게 작성한다.
최소한 Unity와 C#을 배운 학부생이 읽고 아래 내용을 알 수 있어야 한다.

- 이 기능이 게임에서 어떤 역할을 하는가
- 기존에 어떤 문제가 있었는가
- 이번 작업으로 무엇이 어떻게 바뀌었는가
- 어떤 테스트나 확인을 했는가
- 아직 무엇이 남았는가

작성할 때 지킬 규칙:

- 내부 약어를 처음 쓸 때는 풀어쓴다.
  - 예: `Plate`는 전투에서 소환수가 배치되는 칸이다.
  - 예: `Draw`는 소환 후보를 뽑는 흐름이다.
- 클래스명만 나열하지 말고, 그 클래스가 담당하는 역할을 같이 적는다.
- “리팩토링했다”, “정리했다”만 쓰지 말고 무엇을 어디에서 어디로 옮겼는지 적는다.
- 테스트 결과는 숫자만 쓰지 말고 무엇을 확인한 테스트인지 적는다.
- 아직 확인하지 못한 내용은 완료처럼 쓰지 않는다.
- 긴 코드 설명, 전체 파일 목록, 긴 로그는 붙이지 않는다. 필요한 대표 파일만 적는다.
- MCP timeout, Transport 오류, 연결 실패 같은 실행 환경 로그는 WorkLog에 상세히 적지 않는다.
- WorkLog는 리팩토링 내용, 결정 이유, 남은 QA 요청 중심으로 작성한다.
- 작업 중 제안이 거절되거나 방향이 바뀌었으면 왜 바뀌었는지 짧게 남긴다.
- 한 문장은 가능하면 짧게 쓴다.
- WorkLog 파일은 `YYYY-MM-DD.md` 날짜별 파일만 만든다.
- 작업명이나 티켓 ID를 파일명에 붙인 `YYYY-MM-DD_<작업명>.md` 파일은 만들지 않는다.
- 세부 작업 기록은 별도 파일로 만들지 않고 날짜별 파일의 `작업 내용` 또는 `참고 메모`에 짧게 요약한다.
